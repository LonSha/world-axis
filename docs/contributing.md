# 改代码的规矩

## 四条硬约束

1. **零依赖**：不引入 `package.json` / `node_modules`。只用 Node 内置模块（`fs` / `path` / `child_process` / `vm`）。
   临时用到的第三方库（如 jsdom）只装在 `/tmp`，不进仓库，也不得让门禁 `require` 它 ——
   否则要么给仓库引入依赖，要么在别人机器上静默跳过、门禁失效。
2. **产品面不动冻结面**：`FROZEN` 契约逐字冻结。改动导出成员是**显式动作**，必须同步更新冻结串，
   不允许作为其它改动的副作用发生。
3. **单一真源**：同一个事实只允许一处定义（清单见 [architecture.md](architecture.md)）。
   要加第二份副本之前先问：能不能向现有真源取值。
4. **测「没变化」时要把准备阶段排除在测量窗口外**：否则读数里会混进准备期的副作用。

## 一轮迭代的固定动作

```
1. 改代码
2. node tests/run.js                     # 全量回归
3. 受影响的门禁单独再跑一遍（导出面 / 死子面 / 拒收码 / 读数）
4. git diff 核对：改动是否只包含预期的那几个文件
5. 往 ITERATION_LOG.md 追加一条 R 条目：做了 / 为什么 / 影响范围 / 门禁结果
```

**第 5 步不是形式**：本仓的日志是版本条目的单一真源，README 的版本历史只留摘要。
新版本要动 `index.js` 的 `VERSION`、`manifest.json` 的 `version`、以及 `tests/run.js` 里若干处硬编码断言值
（多处字面量，漏一处就是红灯）。

## 不要做的事

- **不要为了过门禁去改实现**：门禁红了先问判据的输入面是不是比事实窄。
- **不要用「看起来很旧」当删除依据**：判据是「被谁引用」。`tools/patch_o17_v2104.py` 名字最旧，但它被专锁引用而必须留下。
- **不要在回归跑着的时候杀掉它**：负向自证里有「注入产品文件 → 跑断言 → 还原」的窗口，
  在窗口内被中断会把探针永久留在产品文件里（v2.80.0 实测事故）。
- **不要把「已登记缺陷」当成「已修」**：诚实边界要显式列出（如锁里的 `KNOWN_OPEN` 表）。报「已全修」比漏修更坏。

## 文档怎么改

- 版本之间的事 → `ITERATION_LOG.md`（单一真源）。
- README 的版本历史只留摘要；`v2.80.0` 及之后的详细条目以日志为准。
- 读数不要写进文档当断言，写「怎么跑出来」；`docs/ERROR_CODES.md` 例外（它是生成物，有 `--check` 兜住）。
- 结论若不随源码变动（如门禁设计口径），才值得写进 `docs/`。
