# 世界枢轴 WorldAxis

> 缝合13个SillyTavern开源世界引擎的**独立扩展**——让镜头之外的世界自行运转并推动剧情。

**纯框架**：不预设任何世界观内容，世界背景由你的角色卡/世界书/用户设定注入。

## 安装
1. 下载 Release 的 `WorldAxis.zip` 解压到 `SillyTavern/public/scripts/extensions/third-party/WorldAxis/`
2. 重启酒馆 → 扩展管理启用「世界枢轴 WorldAxis」
3. 右下角悬浮球 ◈ 打开面板 → 「连接」页配置API通道（至少配 default 或 inference）

## 架构
```
before_reply 链:  导演标签扫描 → 连续性约束注入 → 章节上下文 → 突发事件小纸条
                  → NPC独白推演 → 剧情引导拍 → 世界状态快照落地
after_reply 链:   突发事件推进 → 世界推演(backstage) → 事件演化回合
                  → 记忆L0/L1 → 舆情观察 → NPC档案维护
```

## 核心概念
- **世界推演 backstage**：每轮AI回复后，在后台结算镜头外的世界变化（人物位置/暗流/事实/认知边界/世界脉搏），结果写入聊天隔离的store，下一轮以「连续性约束」注入正文。
- **双轴可见性**：事件 visibility(角色能否感知)×publicity(公众传播度)，hidden级暗流绝不剧透给正文。
- **认知边界**：每个NPC独立知识账本，route=inferred 只能标 suspected。
- **世界脉搏**：pressure 0-3 压力账本，驱动世界自发活跃度。
- **记忆分层**：L0单轮摘要→L1阶段巩固→L2章节回顾→L3长线沉淀→facts版本化→伏笔生命周期。
- **事件演化**：冲突/进度双类型四阶段骰子推进（保底机制防卡死）、势力六态七级、声誉四维五级、经济四气候、风声消散、仇敌录、黑盒秘密、天下大势、影响链。
- **远方/近端事件**：Ledger计数阈值强制触发、cooldown冷却、pending重试、临时标记剥离。
- **world_digest**：每轮结算后生成150-200字世界推演叙事，绝对禁止提及玩家。
- **字数限制体系**：events.desc≤50字、factions.currentGoal≤50字、winds.topic≤10字等全字段截断。
- **事件链ID稳定**：API返回id原样使用、改名不换链、type一旦确定禁改、stall停滞标记。

## 工具与体检（v0.9.1）
- **写入侧台账（v2.6.0）**：设置页/体检入口可查——设置键的**每一次真实写盘**是否落盘（保存 / 迁移回写 / 结构指纹 / 旧键迁移 / 格式复活 / 隔离副本，统一经唯一写出口记账）、失败**来源分类**（「登记项缺 key」「值不可序列化」=实现缺陷 vs「配额已满/隐私模式」=环境问题，两者给不同下一步动作）、最近写入键与字节量、以及写入侧新出现的 def 之外子键（只计量、不剪除）。写失败时**设置页与面板都给出可见告警**，不再无条件报「✓ 已保存」
- **写入侧完整性 + 生效值单源（v2.7.0）**：两件此前不可判定的事现在可判定——**① 「写进去了」拆成「被接受」与「被留住」**：设置键写盘默认**写后读回逐字符比对**（`setItem` 不抛错 ≠ 值真在盘上，配额临界/写入毒化/后台回收下会静默丢弃或截断），失败三分类（missing-after-write / length-mismatch / content-mismatch）并在设置页与诊断包里可见，存档恢复安装（`chatcache.installPack`）同判据并透出 `installStat`——「恢复完成」不再可能是「其实没装进去」。**② 「用户看到的数」＝「磁盘存的数」＝「引擎执行的数」**：区间/枚举/哨兵声明上收到设置键登记表（单一真源），五个模块写路径统一走 `normalize` **写入即归一**，UI 控件区间从声明取（不再硬编码第二份），诊断新增 `settingsBus.writeStaged` 与 `chatcache.install` 两个议题，自检新增三码值域声明校验（声明空转即报错）
- **出口面清册（v2.8.0）**：`node tests/inventory.js [--dead] [--json]` 独立运行（以退出码表达结论）。用「运行时真实导出面」×「静态跨文件引用面」交叉求差，一次打出三类问题：**① 悬空引用**——产品代码引用了运行时根本不存在的成员（如 `WA.pmem.recentText(4)`，被三元守卫吞成空串 ⇒ 静默降级，连日志都没有）；**② 未登记模块**——磁盘上有 `*.js` 而 `tool-diag.MODULE_EXPORTS` 没登记（自检看不见的黑盒）；**③ 死导出**（`--dead`）——函数成员导出后产品代码零引用（与死键同型），并按「仅测试引用 / 常量数据成员」分列备查，避免把「给测试与诊断读的枚举」误判成死代码。UI 层单列：脚本会先尝试装载 `ui/*`，装载得到就参与校验、装载不到才归入「需浏览器复核」，从而把「宿主没装 UI」这类假悬空与真悬空分开
- **出口面契约门禁（v2.8.0）**：`tests/export-contract.js` 生成「跨文件依赖的导出成员」冻结串（52 个命名空间 / 279 个成员 / 3633 字符），`tests/run.js` 的 v2.8.0 块1 以它做**双向**绑定——引用面必须零悬空，定义面任何增删都必须显式更新冻结串（失败信息直接给出精确的「新增/减少」清单）。防的正是「成员被悄悄改名或删掉、调用方静默降级」：接口面变动必须是有人确认过的动作，而不是顺带发生的副作用
- **删除侧完整性（v2.9.0）**：写入侧自 v2.6.0/v2.7.0 起有三层口径（每一次真实写盘是否落盘 / 写进去有没有留住 / 声明之外的新子键），而**删除侧此前一行都没有**——删除是破坏性操作（删错 = 用户数据没了），它不可观测比写入不可观测更危险：面板说「已清理 N 项」，而用户会据此认为空间已腾出。本版把删除收口为**唯一出口**并给出三层对偶：**① 成功计量与失败归因**——`settingsBus.remove()` / `store.removeVerified()` 是设置键与存储键的唯一删除出口，删成功计入 `removes`/`removed`，删失败按来源分桶（`guarded` 删完仍在 / `missing` 登记项缺 key / `setItem` 删除被拒 / `quarantine` 隔离路径 / `legacy` 旧键迁移 / `settings` 设置键出口），**键本就不存在**单独计入 `removeAbsent`（幂等无操作不是删除成功——否则「N 次全部复核通过」可能来自 N 次空操作）。**② 删后读回复核**——`removeItem` 不抛错 ≠ 键真的没了：删完立刻读回，仍能读到即判「这次删除没有发生」（`still-present-after-remove`）。这是删除侧最危险的形态，比抛错隐蔽得多。**③ 当前态判据**——健康巡视与诊断包看的是「最近一次删除的结果」而非历史累计，用户把存储修好后面板立刻转绿（与 `integrityStat.lastOk` 同裁决）。诊断包对两个域各报一条：`settingsBus.removeStaged` / `store.removeStaged` 为 **error**（删完读回仍在：清理报出的「已释放」与实际不符），`settingsBus.remove` / `store.remove` 为 **warn**。**④ 适用范围门禁 G14**（与写入侧的 G13 对偶）：产品代码里的裸 `removeItem` **只能剩受控出口内部那一处**，冻结清单 `{core/store.js: 1, core/settings-bus.js: 0}`，并带负向探针（新加一个裸删文件必须被检出）
- **读侧完整性（v2.10.0）**：写入侧（v2.6.0/v2.7.0）与删除侧（v2.9.0）收口之后，**读侧是最后一块零治理的面**——全库只有一个来源不明的单桶 `stats.failures`，且实测**产品代码零消费**。后果是本仓库最难取证的一类故障：「磁盘上有用户配置但没读成功 ⇒ 回落默认值」与「用户从来没配过」在面板、诊断包、健康分上**完全一样**（用户只会觉得「设置被程序改回去了」，而没有任何线索可查，也永远不会被功能测试发现）。本版把读侧补齐为严格对偶的第三面：**① 单一实现 + 三兄弟齐备**——`noteReadFail(tag, err, prefix)` 与写侧 `noteFail` / 删侧 `noteRemoveFail` 同规格（一处实现、一处自增、按来源分桶 `read`「存储层读取」/ `parse`「值解析」/ `migrate`「迁移」/ `copy`「深拷贝降级」，未知来源动态建桶），store 域对称给出 `noteStoreReadFail`（`bytes` / `activity` / `enumerate`）。**② 三层对偶**——「写后读回校验」（写侧 `verifyFailed`）与「删后读回复核」（删侧 `removeVerified`）在读侧的对应物是**来源追踪**：`stats.readSources` 按 `disk` / `legacy` / `default` / `defaultAfterFailure` 四次分桶，每次读取都记下「这次拿到的到底是用户配置还是兜底」；`lastRead.reason` 给出具体原因（`read-throw` / `corrupt` / `legacy-corrupt` / `disk-null`），`readEx(reg)` 把来源**结构化交还**调用方（`{ok, value, source, reason, key}`，`ok:false` 即「你拿到的是兜底值」）——这是本仓库唯一能判定该故障的出口。**③ 归因不得失实**（本版两次自纠的核心）：`readStat().ok` **只由硬失败（`read` + `parse`）决定**，迁移回写失败与深拷贝降级单列为 `degraded`——把「迁移钩子坏了」报成「读不到配置」会把用户引向错误的排查方向（查存储而非查迁移声明）；v0.1.x 遗留的单桶 `stats.failures` 也在此视图里给出出口（`legacyFailures`），不再「还在涨却没人看」。**④ store 读侧现场**——`keyBytes` 此前 `catch (e) { return 0 }` 把读失败吞成 0 字节（「键是空的」与「读不出来」不可分辨）⇒ 占用表**偏小**；`chatActivityAt` 读失败回落 0 = 「最冷」⇒ 该聊天的诊断键被判为可回收候选（**读失败诱发误删**）；`listWorldAxisKeys` 枚举失败回落空清单 ⇒ 全部键都看不见，面板却照样报出一份「存储很干净」的结论。`storageStat()` 新增 `readFailedKeys`（本次盘点读失败键数，与分桶明细**同口径**）、`readFailedDetail`（本次差值）/ `readFailedCumulative`（累计分列）。**⑤ 双消费端 + G15 门禁**——诊断报告：`settingsBus.readFailed`（`defaultAfterFailure > 0` 走 **error**：用户当前看到的配置不是他配的）、`settingsBus.readSpotCheck`（**error**，对登记表中「磁盘有值」的键做 `readEx` 现场抽查——诊断包里那份配置可信吗）、`settingsBus.readonlyCopy`（warn）、`store.readFailed`（warn）；健康分新增 `storage.readFailed`（−7）/ `storage.readActivity`（−5，误删风险更重）；面板「设置键」页新增读取侧四行 + 存储域一行。**⑤b 读侧裸读点全覆盖**（逆向审计第四轮的产出，见下）：不只是设置总线，store 域的每个读点都归因到来源（`bytes`/`activity`/`enumerate`/`diskRev`/`verify`/`recovery`/`conflict`/`quarantine`/`writerId`），且 `readStat().bySource`
