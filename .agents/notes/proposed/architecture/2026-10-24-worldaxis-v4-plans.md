# Agent Note: WorldAxis V4 双九项计划
Status: proposed

## Problem
WorldAxis 当前版本为 `v2.232.0`。近期 `v3-a`、`v3-ab`、`v3-b`、`v3-c` 和 `v3-op9` 已经把 V3 计划中大量主题机制真实写入产品，包括情境投影、行动桌、资源承载、有限传播、公共协作、地方规则、服务网络、场景回声、连锁冲击、地方路径和玩法蓝图。继续把旧 V3 台账当作待办，会重复建造已经存在的能力。另一方面，产品已有大量页面和引擎，玩家仍需自行把局部能力拼成跨场景、跨周期的连续玩法。

用户要求两份各九项的优化与拓展计划，必须基于仓库当前状态，避免守卫/审计成为第二系统，且规模至少能支撑三天以上的实质功能工作。

## Decision
本仓库采用 V4 双九项作为当前工作纲领：

- [优化提升 V4](../../../../plans/WORLDAXIS_OPTIMIZATION_9_V4.md) 聚焦场景到行动的入口、跨轮行动生命周期、剧情时间成本、人物日常中断、证据驱动判断、健康/地点资格、长局记忆、章节分支连续性和蓝图续局。
- [拓展创新 V4](../../../../plans/WORLDAXIS_EXPANSION_9_V4.md) 聚焦材料生命周期、人口迁移、照护服务、公共议程、共同资源维护、知识实践许可、风险互助、多重归属和世代制度延续。

两条线严格各九项，共十八项，合计估算 482–762 有效工程小时，拆为 A/B/C 三个大批次。估算只计算真实产品业务、owner 接线、正常入口、兼容迁移和必要宿主验证；测试、守卫、审计、文档和页面数量不计作主题功能工作量。

所有项必须遵守以下边界：

- 复用已有 `store`、`playtime/calendar`、人物、资源、认知、关系、事件和世界书真源，不创建平行事实账本。
- 新投影可以聚合，但不得成为第二写入源；写入必须返回原业务 owner。
- 新机制必须改变行动空间、人物选择、资源分配、地点服务、制度结果或长期历史，不能只增加字段、指标、诊断或守卫。
- 每项必须有正常玩家入口、成功与失败/替代路径、视角边界、保存重载和后续场景消费。
- 不再以师徒/成长数值为扩展主轴，不新增治理平台、真实多人联网或公开发布链。

## Alternatives considered
- **继续实施旧 V3 双九项** — 旧方案的主题方向仍有价值，但提交历史证明其中大部分已经落地；继续照单执行会把已完成能力当作缺口，故改为历史参考并由 V4 承接未闭环部分。
- **继续增加守卫、审计和测试平台** — 它们能提高可证性，但用户可感知的主题能力已经落后于元工作，故只保留为每项验收手段，不独立占产品名额。
- **再增加师徒、成长或人物数值系统** — 易于形成新字段和面板，却不能解决跨模块行动连续性，也不符合用户要求的差异化方向，故明确排除。
- **另造统一世界模拟器** — 表面能把模块集中起来，但会产生第二套时间、资源和事实真源；V4 只做薄投影、消费链和既有 owner 的纵向联动。

## Consequences
V4 将研发重心从“已有专项能否被证明”转向“玩家能否在一个世界里连续生活、行动、承担代价并看到长期反馈”。前期需要处理更多跨 owner 接口和宿主行为，单项工时比旧小计划更大；作为交换，计划不再靠新增模块数量制造进度，也能把 V3 已有资产转化为主题体验。

V4 仍是提案，不宣称功能已实现。旧 V3 文件保留追溯但已明确标记为被 V4 取代；唯一当前入口是 `NEXT_PLAN.md` 顶部。

## Verification
在每批实现前后，先以 `git log`、实际导出和调用点复核计划项是否仍是缺口；再运行对应纵向集成测试、`tests/run.js` 以及仓库现有架构/测试面门禁。任何单项若发现已有真实消费链，应缩小为缺口修复或从排期中删除，而不是为了完成计划硬加机制。
