Status: proposed

> **代际状态（2026-10-08 审计）**：本篇的 TP/TX 台账已被 [v2.173.0 之后的双九项计划（O1–O9 / E1–E9）](2026-10-08-worldaxis-o-e-plans.md) **完全取代**。下表所记"基线 v2.158.0"与"TX5–TX9 未开始"已与现场不符：TX1–TX9 九项全部交付，TP 线只剩 TP6/TP8 两项且均卡在现场环境。本笔记按纪律保持 `proposed` 原文不改写，只作历史决策副本；当前台账见 [plans/O_OPTIMIZATION.md](../../../../plans/O_OPTIMIZATION.md) 与 [plans/E_EXPANSION.md](../../../../plans/E_EXPANSION.md)。仍成立的部分是"证据分四栏（源码 / 无头 / 宿主 / 玩家）"这一口径，已被 O1 接管。

## Problem

用户要求基于当前仓库制定两份各九项计划，并辨别过时信息、已完成能力和未闭环玩家路径。当前 manifest.json 与 index.js 为 v2.158.0；README 的当前版本、NEXT_PLAN 的旧 S2/S3 状态和上一代提案的 S3/SP6“未实施”描述落后于源码。直接复制 RP/RX 或 SP/S 会重复建设已交付模块，也会把无头操作锁误读成真实宿主验收。

本轮复跑 /tmp/wa_plan_probe.js：A 聊天 initPreview 后，B 聊天 initConfirm 返回 confirmed:true，B 写入人物“沈舟”和 initFrom；A 发起 summarizer 请求，B 收到响应后 smallSummaries 增加“只属于旧聊天A的港口船期摘要”。两条行为暴露聊天归属缺口，探针 REPO_UNCHANGED:true。pmem 与 actors/profile 的相似 await 写回路径仅确认风险形态，尚未分别作行为复现。

源码已经足够支持制订方案；真实 SillyTavern 的生命周期、手机前后台、种子初始化后持续游玩仍缺验收证据。本文件只记录 proposed 方案，不修改产品实现、测试实现、配置、冻结面或版本。本轮不运行产品全量回归。

## Proposal

本代用 TP1–TP9 表示优化线，用 TX1–TX9 表示拓展线。完整任务定义分别在 [优化提升计划](../../../../plans/TP_OPTIMIZATION.md) 与 [功能拓展计划](../../../../plans/TX_EXPANSION.md)，两份文件各有九项；本笔记只保留选择理由、旧项关系、依赖与统一验收，避免重复十八份任务正文。

优化线先防串聊天，再收口时间入口、提交语义、证据、性能、容量、注入与宿主体验。拓展线先完成用户指定的五项核心方向，再用委托、调查、地点后果和组织运营连接起来。新增功能以“操作→实际状态→已知反馈→重载延续”为交付单位。引擎与图表仍是实现部件，单独存在不自动证明这条玩家路径成立。

## Alternatives considered

**原样延用 RP/RX 或只扩展 SP/S。** 最强理由是编号和历史锁连续，维护成本最低。实际源码已经超过文档状态，继续原样列任务会重复性能台账、种子预览等模块；采用新编号并保留旧交付对照，解决当前优先级与历史事实冲突。

**先做外交和人物玩法，最后修聊天隔离。** 玩家价值最直接，也便于用新功能证明进度。但两个已复现缺陷会把新操作写进错误存档，扩大功能后更难定位；先完成 A 批归属与提交，再并行建设玩法。

**把种子升为整份聊天存档复制。** 最强理由是已有字段无损，避免逐模块维护结构映射。但用户需要相似世界的新局，复制历史进度、私密记忆和运行中义务会违背新局语义；采用受支持结构蓝图与可选静态场景模板，完整存档仍留给已有备份/恢复职责。

**另建外交、物流、任务和组织的独立数据库。** 模块容易自洽，能够较快做出展示。但与现有势力、库存、人物和权限形成第二真源，跨模块结果无法一致；新层主要登记关联、规则与回执，状态与资源执行复用既有真源及候选事务。

**把未知结果交给 AI 文本决定并自动落盘。** 最强理由是适配任意题材，减少人工登记规则。实际难以证明条约、库存和秘密权限成立；AI 可以给提案或待确认描述，持久结果仍要结构预检与业务证据，未知保留未知。

## Acceptance criteria

1. 两份文件各九项，编号连续唯一；每项包含已交付基础、明确增量、边界/依赖及可验证结果。旧项与新项映射可检索，不把旧实体计为新交付。
2. 任务四栏分别登记：源码交付、无头行为、真实宿主、玩家路径。当前摘要、取消、重生成和切聊天场景检查实际状态/落盘/prompt，不以调用计数或测试文件名证明路径完成。
3. 新导出回填 FROZEN2800、模块清册与消费者；新容器登记 __BOUNDED_CAPS 并采用真实写者可执行策略；新注入登记 inject-budget.ACCOUNTS；新设置、拒收码与故障接入设置 UI、见证和 maintain。版本实施时同步 index.js 与 manifest.json。
4. 每个实施版配专锁及 N0–N4 负控制，真源码副本上重跑同判据，锚点不存在/不唯一、原版判据失败或破坏不敏感均明确失败。输出落盘，避免大输出 PIPE 死锁，后续断言不得因异常漏跑。
5. 相关门禁与两份读数现场重跑，证据绑定源码摘要；全量只在用户当时有效的授权与运行纪律下从 node tests/run.js 执行。本次计划仅复跑只读探针与文档校验，不对历史全绿数字作当前承诺。
6. 所有 TX 至少有一个固定端到端场景及取消/重复/串聊天/容量满/重载场景；真实宿主需交互、控制台与最终状态证据。手机性能先采基线，再冻结预算，再评价收益；缺宿主证据保持待验收。
7. 本次文档产出检查两份九项数量、Agent Note 树和格式、相关链接与实际改动清单；对照改前文件摘要证明产品/测试/配置/版本没有本轮写入。

## Risks

稳定 ID 迁移涉及仍按显示名读取的旧接口；若只改蓝图不改消费者，会出现“导入成功但人物无法行动”。TX5 必须给现有读写者明确 alias/ID 映射及存量迁移，分阶段验证，再增加玩法字段。

跨引擎候选复制和精确读面校验有手机性能成本；放宽校验又会重开串聊天或过期写入。以相关依赖读集减少无关拒收，并用 TP6 数据选择优化，不能牺牲整批失败语义。A→B→A 还需生命周期序号，单纯比较 chatId 不足。

物流、条约与合同相互引用，容量治理会影响游戏义务；历史环形挤出不能直接用于在途货物或待履约条款。TP7 先登记暂停/拒收/归档裁决，再实施新增持久容器。

真实宿主事件、页面前后台和新聊天流程依赖 SillyTavern 版本；mini-DOM 不覆盖这些差异。当前没有实机通过证据，该限制只影响实施后完成判断，不阻塞现在交付可评审计划。
