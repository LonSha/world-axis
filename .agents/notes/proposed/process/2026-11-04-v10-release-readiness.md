# Agent Note: V10 发布资格优先于下一轮功能扩张

Status: proposed

## Problem

V9 已在 `2.295.0` / `2434588` 推送，十八项产品能力和专项锁已完成，但交付仍缺三类不能互相替代的证据：完整 `tests/run.js` 零失败结果、真实 SillyTavern 宿主路径、真实手机/存储/长局数据。第九趟全量按用户指令停止，因此不能把前八趟收敛过程写成全量通过；Chromium/CDP 桩宿主也不能升级为真实宿主验收。

仓库已有 O1 的宿主矩阵、U7 的真实宿主边界、U9 的发布前事实报告，但这些决定一直停留在历史计划或专项门禁，没有组成 V9 的发布阻塞闸门。若现在直接继续开新功能双九项，下一轮会继续累积“专项已验、产品未闭环”的交付债务。

## Proposal

先执行 R0 事实基线，再执行 R1 全量回归；只有 R1 取得三要素凭据后，进入 R2 真实 SillyTavern 桌面宿主矩阵。R3 处理真实手机、存储和长局现场，R4 生成发布事实报告并按 `candidate`、`blocked` 或 `deferred` 裁决。执行细则统一放在 [V10_RELEASE_READINESS.md](../../../../plans/V10_RELEASE_READINESS.md)。

## Decision

V10 先作为 **Release Readiness** 计划推进，不立即新增产品功能。执行顺序为 R0 事实基线、R1 全量回归、R2 真实 SillyTavern 桌面宿主、R3 移动/存储/长局现场、R4 发布事实报告与裁决。

证据分为 L0 至 L4：源码门禁、Node 专项/全量、Chromium 桩宿主、真实 SillyTavern 桌面宿主、真实手机或等价实机。低层级证据不得冒充高层级证据。最低发布候选要求是全量三要素通过、V9 关键路径达到 L3、发布事实报告一致、工作树干净；手机/长局/存储若属于结论范围必须有 L4，否则只能标为阻塞或延期并在发布说明中明示。

所有真实宿主路径统一保存交互序列、控制台、操作后状态和重载后状态。现场缺陷按最小 bug-fix 单独处理，并重新运行受影响专项、全量回归和对应宿主路径；环境不可用则保留 `blocked`，不降低断言、不扩大容差、不删功能。

## Alternatives considered

**直接立项下一轮产品双九项。** 最强理由是已有连续的 V7/V8/V9 规划节奏，可以保持产品迭代速度。但它会把 V9 的全量和宿主缺口继续向后推，并让专项绿色掩盖真实交付状态；先闭合发布资格能给后续功能一个可复核基线，因此不选。

**把 Chromium/CDP 桩宿主升级为真实宿主等价物。** 最强理由是当前环境可自动化、成本低且已有浏览器锁。它无法证明 SillyTavern 扩展加载、聊天/楼层/生成生命周期、第三方扩展共存和真实持久化，和现有 O1/U7 边界冲突，因此只保留为 L2 证据。

**不重跑全量，仅沿用前八趟的 24047 通过数。** 最强理由是失败已经逐条清偿，重跑成本高。第八趟仍有一条真实全量断言失败，第九趟没有完成；沿用历史数会违反 `result.json` 三要素门槛，因此不选。

**把手机、存储和长局证据全部从发布范围删除。** 最强理由是当前没有实机环境，可以尽快形成桌面候选。可以把它们标为延期，但不能把涉及这些场景的产品结论写成已验；计划允许 `deferred`，不把缺失数据伪装成通过。

## Acceptance criteria

- V10 计划文件存在并成为 `NEXT_PLAN.md` 当前入口。
- 新提案笔记符合 Agent Note 的 proposed 结构，并记录至少四个真实备选方案。
- R1 只接受 `result.json` 的 `status=passed`、失败 `0`、`unchanged=true`。
- R2 的 V9 关键路径逐条达到真实 SillyTavern L3，且每条具备交互、控制台、最终状态、重载状态四类证据。
- R3 的手机/存储/长局结论有 L4 数据；缺少现场时明确为 `blocked` 或 `deferred`。
- R4 报告区分通过、阻塞和未覆盖，工作树干净后才允许进入 candidate 复核。

## Risks

- 真实宿主或实机环境不可用，计划可能长期停在 blocked；应保存环境诊断，不用桩宿主替代。
- 长全量回归仍可能受 proot、Chromium 资源或时限影响；应保留任务日志并区分环境失败与产品失败。
- V9 关键路径若暴露稳定缺陷，会增加最小修复后的专项、全量和宿主复验成本；不应借机扩大 V10 功能范围。
- 多层证据整理可能造成文档重复；以矩阵和事实报告为聚合面，源日志和状态快照作为证据原件。

## Consequences

V10 的第一批工作主要是证据、环境和发布纪律，不会立即产生新的玩家功能；它会增加一次长全量和真实宿主/实机协调成本。作为交换，下一次发布判断将明确区分源码、隔离运行时、桩浏览器、真实宿主和真实设备，不再把专项结果当全量或实机结论。

V9 计划和历史笔记继续保留其当时事实，不被改写成新决定。`NEXT_PLAN.md` 将只指向 V10；明显反事实的当前入口会被修正，历史段落继续保留。V10 完成后，才根据现场稳定缺陷和玩家路径证据决定是否创建真正的 V10 产品功能计划。

## Verification

- 计划包含 R0–R4、L0–L4 证据分层、V9 关键路径矩阵和 candidate/blocked/deferred/released 状态规则。
- 提案笔记引用唯一的 V10 计划文件，并记录真实考虑过的替代方案。
- 落盘后运行 Agent Note 格式/树校验、`git diff --check`、证据索引检查；本提案本身不宣称产品测试或宿主验收通过。
