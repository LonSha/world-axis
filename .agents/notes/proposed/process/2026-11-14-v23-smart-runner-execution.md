# Agent Note: V23 regression tiers execute distinct workloads

Status: proposed

## Problem

L2 and L3 currently execute smoke, so neither incremental coverage nor isolated full regression is exercised. The V23 scenario shares the V21 section, which makes targeted selection unnecessarily broad. A zero-match incremental run must never become a passing run or an implicit full run.

## Proposal

Keep smoke as L1 and existing static gates as L0. L2 derives changed paths from Git, walks literal test dependencies and namespace consumers, and maps matching evidence files to selectable sections from test-layers. Uncovered JavaScript changes, empty selection and shared-context selection refuse with nonzero status. Explicit --only-v-section is a declared targeted subset rather than a claim of complete change coverage. --plan prints the concrete workload without execution. L2 and L3 invoke isolated-runner.launch in a child process with explicit selection arguments; inherited WA_ONLY_SECTION is removed so L3 always remains full. Preserve the existing isolated runner's candidate-copy, source-digest, lock and summary contract. Report time budgets as limits, not measured speed guarantees. Move only the V23 scenario into its own section and register the scheduler regression there.

## Scope and gate

Staged fix limited to tools/smart-runner.js, tests/smart-runner-v2408.js and the V23 section in tests/run.js, plus this note. Budget 400 changed lines. Baseline 46ce63d: L2/L3 point to smoke; unknown tiers fall through to the same path. Verification uses real temporary Git repositories, actual child execution probes, CLI refusal and in-memory source mutations. L3 is verified through its invocation contract only until all 18 items satisfy the plan. Never launch an unselected tests/run.js during this stage. Stop on source pollution, missing selected-work evidence, or regression in the existing layer gate.

## Alternatives considered

A new handwritten list of engine-to-test assignments is cheap to start but drifts whenever tests move. Reusing smoke avoids new mapping but repeats the false coverage problem. Running every test that mentions store provides conservative coverage but can take full-regression time; L2 therefore reports selected sections and enforces a bounded budget, while unresolved coverage requires L3 at final acceptance.

## Acceptance criteria

Each tier produces distinct execution evidence. L2 selects real affected sections and refuses empty/uncovered input. L3 invokes the existing isolation boundary without selection, and errors propagate. Plans never execute tests. Mutating the L3 target to smoke or suppressing L2 selection makes the same behavioral assertions fail.

## Risks
Static dependency matching cannot prove all dynamic consumers. L2 is bounded incremental evidence, never a substitute for final full regression. Large changes may exceed its time budget and fail. The existing pruning mechanism can retain unsafe legacy setup sections; isolated execution logs remain the authority for actual workload and timing.
## Findings during verification (superseding the first cut of the selector)
The first selector was wrong in three measured ways, all now judged by `tests/smart-runner-v2408.js`:
1. Aggregate hosts counted as consumers. `tests/run.js` is claimed as evidence by 17 sections, and its `const LOAD = [...]` list mentions every product file once. Nine V23 engines therefore matched *only* through that list, while the scenario that truly calls them matched nothing. `run.js`, `inventory.js`, `product-files.js`, `mock.js`, `ui-gate-sync.js`, `export-contract.js`, `dead-export-gate.js` are now excluded as hosts; the exception list is exact, not a pattern.
2. The real consumer speaks namespaces, not filenames. `scenario-v62-…` drives nine engines through `WA.<camelCase>` and never writes `commodity-circulation`. The selector now matches the camel-case namespace. Its first form also excluded `.` from the left boundary, which made every `WA.x.y(...)` call invisible; the guard is now on the suffix only (`storefrontWindow` still must not match `store`).
3. Judgement 2 never fired. Section evidence holds bare filenames while the changed set holds `tests/…`, so the lookup key never matched: editing a section's own evidence file still reported it uncovered. Now normalised by basename.
Also: L3 was passed through the selection refusals, so `--tier=3` reported `uncovered-change` and the `full-regression-gated` code was unreachable. A full run has no selection by definition; the gate now covers execution only, so `--tier=3 --plan` reports the full plan while executing still requires `--allow-full`. `tests/run.js`, `tests/isolated-runner.js`, `tools/smart-runner.js`, `tools/isolated-run.js` and this lock are registered as the scheduler self-face: the ownership table consumes product surfaces, not the harness itself, so L2 would otherwise be permanently unusable for the task that builds L2.
A fourth gap, found by running L2 against this worktree: `tests/segment-extract-v2400.js` is pinned by a `runLock` section and is therefore `selfContained: false`, so selection can never claim it, and it landed in `uncovered` — meaning L2 would permanently refuse the very common case of editing a baseline constant. Its real verification surface is L1: it is a member of the smoke fast set. The fast set is now **derived from `tools/smoke.js`** (its `rel:` entries) rather than hard-coded here, and such files are reported as `fastFace` ("verified by L1, its ownership section is shared context") instead of `uncovered`. Deriving rather than whitelisting keeps the criterion falsifiable: a file the fast set does not name still refuses. With this in place, `uncovered` is empty on this worktree and the only L2 refusal is the honest `wide-impact` (74 sections against a cap of 10).
## Measured readings (this worktree, 20 changed files: 13 product / 3 test / 4 others)
L2 selection is honest and refuses: 74 selectable sections exceed the 10-section cap, so the reading is `wide-impact` with the untruncated reason, not a green light. Hand-picked run of 13 changed product files earlier produced 60 sections under a stem-word match and 36 under literal-path match; the namespace criterion finds the true consumers (each V23 engine now matches the V23 section). Baselines updated as a consequence: `BASE_SECTION_CC` 442 → 443, `BASE_TEST_FILES` 557 → 558 (face 558 / orphans 0). `tools/isolated-run.js` does not move the file face because `tools/` is outside `product-files.testFiles()`.
## L2 cost floor: the 3-minute tier is not reachable this version
Measured through the real delegation path (`node tools/isolated-run.js --only-v-section '<one section>'`), one targeted isolated run took **405s** against the declared budget of 240s, so the honest outcome is `budget-exceeded` (SIGKILL, no isolated reading), never a pass. The delegation chain itself is proven live: `tools/smart-runner.js` spawned `tools/isolated-run.js`, which prepared a candidate tree and ran `tests/run.js --only-v-section …` inside it with `unchanged: true`.
The cost is not in the selected work — the V23 scenario runs in 3.6s standalone — and not in candidate preparation. `tools/prune-sections.js` reports `wrappedCount: 409` (proven effective: skipped sections print `已跳过：分层选区未选中`) but also `wrapUnsafe: 14` with `markedLines: 3785`: fourteen sections have unbalanced net brackets and are therefore "marked but not wrapped", so their bodies still execute. That batch includes the one-section-with-75-spawns group added for the orphan assets. The floor is set by those 3785 lines and is **nearly independent of the selection**.
Consequence recorded rather than papered over: the tier budget was set to 600000ms (1.48x the measured 405s) and documented as an upper bound, not a speed claim. Reaching a true 3-minute tier requires making those 14 sections wrappable, which belongs to the pruning tool, not to the scheduler. Two further measured facts are on the record: an interrupted run leaves a stale regression lock that must be recovered explicitly (the runner refuses rather than forcing its way in — that is the designed behaviour, and `recoverLock` is the documented path), and running the isolated regression concurrently with `tools/smoke.js` on this machine makes `tests/segment-extract-v2400.js` fail 4 assertions purely from memory pressure — it passes 126/126 when run alone. Isolation and smoke must not be run concurrently here.
